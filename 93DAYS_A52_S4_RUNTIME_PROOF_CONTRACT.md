## 1. Goal

S4 proves that the A52 `narrative-runtime-artifact` v1 can leave the editor as a self-contained HTML document and be consumed at browser runtime.

This is **compiler validation**, not a new player-runtime roadmap.

The proof must demonstrate:

1. a valid compiled artifact reaches exported HTML through the existing Twine publishing boundary;
2. browser JavaScript can locate, parse and recognize the versioned artifact;
3. the authored project identity and fresh initial-runtime moment can be read and rendered;
4. malformed/missing/unsupported artifacts fail visibly and atomically.

S4 does not implement narrative gameplay.

## 2. Why a dedicated proof shell is required

S3 can bind transient artifact data to the host Story's configured Story Format. Existing general-purpose formats do not understand the A52 artifact and therefore cannot prove artifact consumption.

S4 adds a small A52-owned **runtime-proof Story Format source** used only for validation.

It still delegates Story/Twine serialization and placeholder binding to the existing:

`publishStoryWithFormat()`.

S4 must not modify generic publisher semantics.

## 3. Runtime-proof shell capability

The proof shell may only:

- locate the generated Passage tagged `93-days-runtime-artifact`;
- read its text;
- call `JSON.parse()`;
- validate the compatibility envelope needed by the proof:
  - `format === "narrative-runtime-artifact"`;
  - `version === 1`;
  - authored projection is an object;
  - initial runtime simulation is an object;
  - initial day/minute are integer values in the expected basic ranges;
- render read-only proof facts using DOM `textContent` / inert attributes.

The proof may display:

- proof status;
- artifact format/version;
- authored project name;
- source schema version;
- initial day/minute;
- counts of authored Characters, Story nodes and Narrative Moves.

No additional narrative meaning is derived from those counts.

## 4. Hard no-go: no second runtime

Proof-shell JavaScript must **not**:

- evaluate Narrative Guards or Conditions;
- resolve Moves or Outcomes;
- apply Outcome effects;
- advance simulation time;
- rank NPC/reaction decisions;
- resolve schedules or Actual Presence;
- mutate cognition, body, injury, relationship, item or Story runtime state;
- create runtime occurrences;
- implement Story execution/interruption semantics;
- use randomness;
- interpret artifact strings as executable JavaScript.

It must not contain a copied subset of canonical evaluator logic.

Canonical mechanics remain owned by the existing TypeScript runtime modules.

## 5. Proof preparation

Conceptual contract:

```text
prepareNarrativeRuntimeProof(project, hostStory, appInfo)
  -> blocked { diagnostics }
  -> ready {
       artifact,
       diagnostics,
       story,
       html
     }
```

The proof preparation:

1. calls the already verified S3 `prepareNarrativeStoryExport()`;
2. returns its blockers unchanged;
3. binds the resulting transient Story to the dedicated proof Story Format source using `publishStoryWithFormat()`;
4. returns the resulting self-contained HTML.

It must not call the host Story Format loader.

Reason: the proof shell itself is the controlled validation runtime. The host format remains relevant to normal S3 export, not to S4 compiler validation.

## 6. Single generated artifact Passage

S4 reuses the S3 transient Story unchanged.

It must not:

- add another artifact copy;
- invent a parallel runtime payload;
- persist proof-specific Passages;
- mutate the generated artifact Passage before binding.

The exact canonical artifact JSON remains the one generated by S2/S3.

## 7. Browser execution contract

On page load the proof shell must transition its visible root from `loading` to one of:

- `ready`;
- `error`.

For a valid artifact it renders the required read-only facts.

For failure it renders a stable human-readable error and must not render a false ready state.

Minimum failure categories:

- generated artifact Passage missing;
- artifact JSON malformed;
- unsupported artifact format;
- unsupported artifact version;
- missing/invalid required proof-readable start state.

The shell may group failures under one visible error status; tests must still prove each compatibility class cannot become ready.

## 8. Safety / inert data contract

Artifact/project content is data.

The shell must:

- rely on Twine publisher escaping for generated Passage text;
- use `JSON.parse()`, never `eval`, `Function` or script injection for artifact content;
- render artifact-derived strings through `textContent`, not `innerHTML`;
- never copy authored script/style from the host Story (already guaranteed by S3).

A project name or authored string containing HTML/script-like text must remain inert.

## 9. Determinism

Given identical:

- prepared transient Story;
- proof Story Format source;
- app info;

`publishStoryWithFormat()` produces the same proof HTML bytes.

The proof shell source contains no:

- timestamp;
- random id;
- locale-dependent generated value;
- current session state.

The existing Twine `creator-version` field remains an explicit app-info input.

## 10. UI / explicit validation action

The existing Narrative Export panel may expose a second explicit action:

**Compiler proof HTML**

This is separate from S3's normal **Собрать HTML** action.

The proof action:

- is disabled when preparation is blocked;
- generates the dedicated proof HTML;
- downloads it through existing `saveHtml()`;
- uses a distinguishable filename such as `.compiler-proof.html`;
- does not mark authoring dirty;
- does not create an authoring Undo/Redo entry;
- does not advance live/Preview runtime.

The panel must label the output as validation-only, not as the final player-facing game runtime.
